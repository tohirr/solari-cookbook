passk a worked example · built on Solari · outcomes verified inside the VM

Your agent passed once. Will it pass again?

passk forks one Solari desktop snapshot k times, runs the same agent on every fork, verifies the result inside the VM instead of trusting what the agent says, and reports how reliable it is and why it fails when it does. This page is one task under two prompts: 38 scored runs on gpt-5.6-luna, $1.48 of model spend.

These benches were run while building the tool, at small k on a budget model. They show what a bench and a comparison contain; they are not findings about any model, and they will be re-run.

The task

The support queue is open in the browser. Assign every open ticket to its customer's account owner; the owners are on the Team page. Any open ticket that has been open for more than three days should be high priority. Leave closed tickets alone. Save each row you change.

A support queue served from inside the desktop: twelve tickets, the account owners on a second page, a three-day rule, two customers called Acme. 19 checks grade one fact each, 7 of them guards on things that must not change; a run passes only if every check passes when read from the app's own state file after the agent stops.

The agent followed the correct task interpretation but used `type` to change dropdowns instead of the reliable single-letter keypress method used in the passing run. That interaction did not consistently update selections when the fields already had another value, leaving tickets 102 and 105 with incorrect assignees and priorities.

How it works

Prepareboot a template, run the task's setup once, snapshot, kill
Validateon one fork, the checks must fail untouched and pass after the golden steps, or no bench
Run ×kfork the snapshot, agent loop on each fork, checks inside the VM
Reportpass@1 with its interval, pass^k, effort and cost per run, a hypothesis per failure
Comparechange one thing, fork the same snapshot again, measure the delta per check
